# kit 基础库设计文档

## 1. 项目定位

`kit` 是团队 Go 项目的基础设施工具库，统一封装错误、日志、HTTP、SQL、Redis、Kafka 等通用能力。

目标不是成为完整业务框架，而是提供稳定、简单、可复用的基础能力，减少业务项目重复封装。

## 2. 设计原则

- 最小封装：保留底层库常用 API 风格，避免过度抽象。
- 稳定优先：公共 API 调整优先考虑已有调用方影响。
- Context 优先：涉及 I/O 的能力优先提供带 `context.Context` 的方法。
- 不主动引入新依赖：现有能力能满足时不新增第三方库。
- 分阶段迭代：先修复明确问题，再逐步标准化和扩展。

## 3. 模块边界

| 模块 | 职责 | 不负责 |
|---|---|---|
| `errors` | 错误包装、错误码、错误分类判断 | 业务错误码注册中心 |
| `log` | 日志初始化、结构化日志、上下文日志 | 链路追踪系统 |
| `http` | HTTP Server、中间件、统一错误响应 | 业务路由、业务响应结构 |
| `sql` | 数据库配置、连接、事务、懒加载 DB | ORM、SQL 生成器 |
| `redis` | Redis 客户端、缓存语义、分布式锁 | 复杂缓存框架 |
| `kafka` | Kafka 生产者、消费者基础封装 | 死信队列、复杂重试编排 |

## 4. 日志设计边界

`log` 包负责日志级别、输出位置和输出编码格式，例如 `json` 或 `console`。

`http` 包只负责访问日志字段采集，例如 `method`、`path`、`status`、`request_id`、`request_time` 等。

HTTP 访问日志最终仍通过 `log.WithFields(...).Info("access")` 输出，因此项目日志格式只需要在 `log.InitLogger` 中定义。

`http.ServerConfig.AccessLogFormat` 和 `DefaultAccessLogFormat` 已废弃，仅保留兼容，不再参与访问日志格式化。

## 5. 当前架构

```text
业务项目
  ↓
github.com/tiamxu/kit
  ├── errors
  ├── log
  ├── http
  ├── sql
  ├── redis
  └── kafka
```

各模块之间保持低耦合，允许基础模块被其他模块使用：

- `http/sql/redis/kafka` 可以依赖 `errors`
- `http/sql/kafka/errors` 可以依赖 `log`
- 禁止业务模块反向进入基础库

## 6. 阶段一稳定化内容

阶段一目标是“够用稳定”，只处理明确 bug 和高风险点：

1. 修复 PostgreSQL DSN 密码拼接问题。
2. 修复 CORS `*.domain.com` 通配域名匹配问题。
3. 降低 `TimeoutMiddleware` 中 goroutine 操作 `gin.Context` 的风险。
4. 明确 `log.InitLogger` 只允许初始化一次。
5. 增加 `redis.NewClientCtx`，允许调用方控制初始化生命周期。
6. 构造函数 nil 参数返回明确错误，不再 panic。
7. Redis 锁释放和续约校验 Lua 返回值。
8. Kafka Producer 默认同步发送，保证重试语义可靠。

## 7. 后续迭代方向

### 6.1 API 标准化

- HTTP Server 创建和启动流程拆分。
- 明确稳定 API 和废弃 API。
- 错误码前缀和错误响应映射标准化。

### 6.2 能力增强

- SQL 慢查询日志和更多 Context 方法。
- Redis 锁重试支持 Context 取消。
- Kafka 消费者重试、批量消费、死信队列按需扩展。
- 日志字段标准化和脱敏能力按需扩展。

### 6.3 质量建设

- 优先使用编译检查、现有测试、静态检查和关键逻辑人工自检。
- 外部服务相关能力如需新增测试，先确认测试范围和运行环境。
- README 和 `doc/接口文档.md` 随 API 变化同步维护。
